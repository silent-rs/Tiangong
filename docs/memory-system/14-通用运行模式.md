# 14. Memory 通用运行模式（MCP / Daemon / 配置页 / 自更新）

Memory sidecar 二进制 `tiangong-memory-sidecar` 除作为天工插件运行外，还可以独立服务第三方 Agent。所有模式共享同一份数据（`<storage_root>/memory/`）和同一个 Leader 选举：同一时刻只有一个进程写入，其他进程经 IPC 转发。

## 命令一览

| 命令 | 作用 |
|---|---|
| 无参数 | 天工插件 sidecar（由宿主拉起，行为不变） |
| `--mcp` | stdio MCP Server，客户端断开即退出 |
| `--daemon --token <令牌>` | 在后台启动 HTTP REST 服务，就绪后命令返回 |
| `--daemon --foreground --token <令牌>` | 前台运行 daemon（适合 systemd / launchd 托管），Ctrl+C / SIGTERM 退出 |
| `--stop` | 停止后台 daemon，等待进程退出后返回 |
| `--config [--host] [--port] [--no-open]` | 打开浏览器配置页（可远程），点击"完成并关闭"后退出 |
| `--check-update` | 检查天工官方插件目录是否有新版本，不改文件 |
| `--update` | 下载新版本并替换当前程序 |

以上模式互斥。存储根默认 `~/.tiangong`，可用环境变量 `TIANGONG_STORAGE_ROOT` 指定。

## 与天工的关系

- **天工内**：WASM 插件直接接入 Agent 对话生命周期，调用方无需做任何事：
  - `on_session_ready` / `on_turn_started`：缓存会话快照，重置本轮回忆标志；
  - `recall_memory` 工具 + prompt 段落：按需回忆；
  - `on_turn_finished`：从完整会话快照提取本轮（用户输入、工具调用、产物），提交增强反刍；每 10 轮触发 Meta 反刍；
  - `on_session_ended`：触发 Meso（工作区级）整理。
- **第三方 Agent**：拿不到天工的会话结构，需要按下面的"生命周期接入约定"显式上报。上报内容由 `tiangong_memory::external::ExternalTurn` 转换成与天工相同的 `EnhancedTurnResult`，走同一条反刍链路。
- 天工与外部进程同时运行时，先启动的成为 Leader，后启动的成为 Follower；Leader 退出后 Follower 自动接替。天工以 stdio 拉起的 sidecar 在 Follower 身份下同样应答宿主请求（经 IPC 转发给 Leader），因此外部 daemon 先运行不影响天工使用记忆。
- `workspace` 可传项目绝对路径，按天工规则取末级目录名，同一项目在天工和外部 Agent 中的记忆互通。

## 生命周期接入约定（第三方）

MCP 只提供模型需要主动决策的两个工具，其余操作属于生命周期或管理动作，不占用模型的工具上下文，通过 daemon 的 REST 接口由 Agent 的 hook 或脚本调用：

| 时机 | 调用方 | MCP 工具 | REST 接口 |
|---|---|---|---|
| 需要历史背景、项目约定时（回忆） | 模型 | `memory_recall` | `POST /api/v1/recall` |
| 用户要求记住、得出长期结论时（记忆） | 模型 | `memory_remember` | `POST /api/v1/memories` |
| 回合结束 | hook / 脚本 | — | `POST /api/v1/turns` |
| 会话结束 | hook / 脚本 | — | `POST /api/v1/sessions/end` |
| 快速检索（不调用 LLM） | 脚本 | — | `POST /api/v1/search` |
| 列表 / 归档 | 脚本 | — | `POST /api/v1/memories/list` / `POST /api/v1/memories/forget` |
| 状态 | 脚本 | — | `POST /api/v1/status` |

`/api/v1/turns` 只做入队，立即返回，不会阻塞对话。只接入 MCP、不上报轮次时，记忆只来自模型主动调用 `memory_remember`；想要和天工一样自动从对话中提炼记忆，需要在回合结束和会话结束时调用上面两个 REST 接口。

## MCP 接入

```json
{
  "mcpServers": {
    "tiangong-memory": {
      "command": "/path/to/tiangong-memory-sidecar",
      "args": ["--mcp"]
    }
  }
}
```

MCP 只暴露 `memory_recall`（回忆）和 `memory_remember`（记忆）。`initialize` 返回的 `instructions` 说明了两个工具的使用时机，大多数客户端会把它带进模型上下文。工具结果同时提供文本和 `structuredContent`；参数错误返回 `isError: true`，未知工具返回 JSON-RPC `invalid_params`。

## Daemon

```bash
tiangong-memory-sidecar --daemon --token <令牌> [--host 127.0.0.1] [--port 7717]
tiangong-memory-sidecar --stop
```

- **令牌由用户设置**：`--token` 或环境变量 `TIANGONG_MEMORY_TOKEN`，至少 8 个字符，不能含空白。未设置时拒绝启动。
- **后台运行**：父进程派生一个脱离终端会话的子进程（Unix `setsid`，Windows `DETACHED_PROCESS`），等到服务真正就绪后才返回；启动失败会打印日志尾部。令牌通过环境变量传给子进程，不出现在进程命令行里。
- 同时只允许一个 daemon，重复启动会报错并提示先 `--stop`。
- 默认只监听 `127.0.0.1:7717`；`--port 0` 使用随机端口。
- 发现文件：`<storage_root>/memory/daemon.json`（`pid`、`url`、`version`，**不含令牌**，权限 0600），退出时删除。
- 日志：`<storage_root>/memory/daemon.log`。
- `--stop`：Unix 发送 SIGTERM 让服务优雅退出（释放 Leader 租约、删除发现文件），等待最多 15 秒；Windows 使用 `taskkill`，Leader 租约由心跳超时回收。
- 鉴权：`Authorization: Bearer <令牌>` 或 `X-Memory-Token: <令牌>`。
- `GET /api/v1/health` 不需要鉴权；`GET /api/v1/tools` 列出全部操作和 JSON Schema（比 MCP 多出生命周期与管理操作）；`POST /api/v1/tools/<name>` 按名称通用调用。
- 状态码：参数错误 400，未授权 401，未知工具 404，Memory 已禁用 503，内部错误 500，错误体为 `{"error": "..."}`。

示例：

```bash
curl -s -H "Authorization: Bearer $TIANGONG_MEMORY_TOKEN" -H 'Content-Type: application/json' \
  -d '{"session_id":"s1","workspace":"/path/to/proj","user_input":"...","assistant_output":"...",
       "tool_calls":[{"name":"write_file","path":"/path/to/proj/a.rs","summary":"写入"}]}' \
  http://127.0.0.1:7717/api/v1/turns
```

## 配置页

配置页是 Memory 唯一的配置入口，命令行不再提供逐项配置参数。

```bash
tiangong-memory-sidecar --config [--host <地址>] [--port <端口>] [--token <令牌>] [--no-open]
# 已安装天工时等价于：
tiangong memory config [--host <地址>] [--port <端口>] [--no-open]
```

- 缺省只监听 `127.0.0.1` 的随机端口，URL 带一次性令牌（160 位随机量），默认用系统浏览器打开。
- **远程配置**：`--host 0.0.0.0`（或本机网卡地址、主机名、IPv6）监听外部网卡，配合 `--no-open` 只打印链接，在其他机器的浏览器中打开。`--port` 固定端口便于防火墙放行；`--token` 可指定令牌（至少 8 个字符，缺省随机生成）。
- 远程配置走明文 HTTP，页面中填写的 API Key 会在网络上传输，启动时会打印警告。只在可信内网使用，或保持 `127.0.0.1` 并通过 SSH 隧道访问：`ssh -L 8800:127.0.0.1:8800 <主机>` 后在本地浏览器打开服务器打印的链接。
- 页面与天工插件设置页是同一份 `memory.html/js/css`：只有当页面是顶层窗口（没有嵌在天工的 iframe 里）且服务端注入了 `window.__MEMORY_STANDALONE__` 时才进入独立模式，改用 `POST /view/<method>` 调用本机服务，方法和载荷与 WASM `handle_view_message` 一致。页面使用相对路径请求，因此远程访问无需额外配置。
- "完成并关闭"按钮只在独立模式下由脚本创建，天工内的设置页中不存在该元素。点击时先保存未提交的配置，再调用 `POST /close`，服务随后退出。
- 独立运行时通常没有天工的模型列表（`models.json`），此时在"记忆文本模型"里选择"自定义在线端点"，直接填写地址、模型名、协议（OpenAI 兼容 / OpenAI Responses / Anthropic / DeepSeek）和 API Key，可用"探测"按钮发一次极短补全验证连通性。

## 自更新

```bash
tiangong-memory-sidecar --check-update
tiangong-memory-sidecar --update
```

更新来源与天工安装插件相同（`plugins-index/catalog.json`，可用 `TIANGONG_PLUGIN_CATALOG_URL` 覆盖地址），信任根固定为内置官方公钥，不可覆盖：

1. 从目录取 `memory` 的最新版本，版本不高于当前则直接返回；
2. 下载当前平台的 `release.json` 与签名，用官方公钥（minisign）验签，并校验发布者为官方、插件 ID 与版本一致；签名不通过时不会下载二进制；
3. 流式下载 sidecar，sha256 必须同时匹配目录和签名清单；
4. 运行候选程序 `--version`，版本号必须一致；
5. 在同目录原子替换当前程序（Windows 先把运行中的旧文件改名再放入新文件）。

限制：
- 由天工插件管理器安装的副本（同目录有 `release.json`）拒绝自更新，应在天工中更新插件，否则会破坏宿主的签名校验。
- 更新只替换文件，已在运行的后台 daemon 仍是旧版本，需要 `--stop` 后重新启动；命令会提示这一点。
- 同目录更新有文件锁，避免并发更新。

## 代码位置

- `plugins/tiangong-plugin-memory/core/src/external.rs`：外部轮次输入与工作区归一化。
- `plugins/tiangong-plugin-memory/sidecar/src/service.rs`：各模式共用的服务层。
- `plugins/tiangong-plugin-memory/sidecar/src/mcp.rs`：MCP 工具定义与 ServerHandler。
- `plugins/tiangong-plugin-memory/sidecar/src/http.rs`：Silent HTTP（daemon 路由、配置页）。
- `plugins/tiangong-plugin-memory/sidecar/src/daemon.rs`：后台进程派生、发现文件、`--stop`。
- `plugins/tiangong-plugin-memory/sidecar/src/update.rs`：官方目录自更新。
- `plugins/tiangong-plugin-memory/sidecar/src/main.rs`：命令行模式分派。

## 内置本地模型

嵌入 / 重排模型选择"内置"时，Memory 在本机用 ONNX Runtime（[fastembed](https://github.com/Anush008/fastembed-rs)）推理，不需要任何在线服务。模型按档位固定，首次选择时后台下载，下载与加载完成前召回自动降级（BM25 + 其他已就绪组件），就绪后无需重启即生效。

| 档位 | 嵌入模型（维度） | 重排模型 | 首次下载 |
|------|------------------|----------|----------|
| 低 | bge-small-zh-v1.5（512） | bge-reranker-base | 约 320 MB |
| 中（默认） | bge-base-zh-v1.5（768） | bge-reranker-base | 约 400 MB |
| 高 | bge-m3（1024，多语言） | bge-reranker-v2-m3（多语言） | 约 1.2 GB |

- 全部使用 int8 量化 ONNX，CPU 推理，最多占用一半核心（上限 4 线程）。
- 模型保存在 `<存储根>/memory/models/<模型名>/`，多个档位可共存，切换档位后回到原档位无需重下。
- 每个文件按固定 revision 下载并校验大小与 sha256，校验不过会丢弃并换源重下。
- 下载支持断点续传；多个 Memory 进程共享同一存储根时只有一个进程下载（文件锁）。
- 配置页在"记忆嵌入模型 / 记忆重排模型"一行显示当前档位的模型、下载进度和就绪状态。

### 平台支持与 ONNX Runtime

| 平台 | ONNX Runtime 来源 | 系统要求 |
|------|-------------------|----------|
| macOS（Apple Silicon）、Windows x64 | 编译时静态链接 | 无额外要求 |
| Linux x86_64 / aarch64 | 首次使用时下载微软官方 `libonnxruntime.so` 1.24.1（约 18~22 MB），运行时加载 | glibc ≥ 2.27、libstdc++（GLIBCXX ≥ 3.4.22）：Ubuntu 18.04+、Debian 10+、RHEL/Rocky 8+ |
| 其他 Linux 架构 | 不支持 | 配置页显示"当前平台不支持"，请改用在线端点 |

Linux 不静态链接的原因：ONNX Runtime 的 Rust 绑定为 Linux 提供的预编译静态库依赖 glibc 2.38+，在 Ubuntu 22.04 等发行版上无法构建。官方动态库的 glibc 基线低得多，因此改为按需下载后在进程内加载。

- 运行库保存在 `<存储根>/memory/models/onnxruntime/1.24.1/<平台>/`，与模型一样校验大小与 sha256、支持断点续传；只由 Memory 进程加载，不修改 `LD_LIBRARY_PATH`，也不依赖系统安装的 ONNX Runtime。
- 加载失败（例如系统 glibc 过旧）时，配置页显示具体原因，召回降级为 BM25 与其他已就绪组件。

### 下载源

按顺序尝试，同一文件断线后换下一个源续传：

1. `TIANGONG_MEMORY_MODEL_MIRROR`（可多个，逗号分隔）；
2. 天工官方 OSS：`https://silent-tiangong.oss-cn-hangzhou.aliyuncs.com/memory-models`；
3. ModelScope（国内 CDN）；
4. hf-mirror.com；
5. huggingface.co。

镜像只需按 HuggingFace 的路径结构提供文件：`<基地址>/<仓库>/resolve/<revision>/<文件路径>`；也可以写成含 `{repo}`、`{revision}`、`{path}` 占位符的模板。内容一律按清单校验，镜像不需要被信任。

Linux 运行库只从自定义镜像与官方 OSS 下载（ModelScope / HuggingFace 不托管），路径为 `<基地址>/onnxruntime/1.24.1/<linux-x86_64|linux-aarch64>/libonnxruntime.so.1.24.1`。

内网部署时可把官方 OSS 的 `memory-models/` 目录（含 `onnxruntime/`）整体同步到内网，再设置：

```bash
export TIANGONG_MEMORY_MODEL_MIRROR=http://mirror.intra/memory-models
```
